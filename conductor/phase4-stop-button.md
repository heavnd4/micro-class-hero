# 彻底解决长时间任务无法中止的问题：一键停止机制方案

## 1. 需求背景
当用户在运行长耗时任务（如批量视频转录或大量图片 OCR 处理）时，如果遇到异常卡死或需要临时中止任务，当前只能强制关闭 GUI 窗口。这不仅体验不佳，且后台启动的 FFmpeg 或 PaddleOCR 子进程可能会以僵尸进程的形式残留，持续占用内存和 CPU。

## 2. 核心架构设计
此方案的核心是在主线程（GUI）和工作子线程（视频处理）之间建立一个安全的“中断通信机制”，即通过一个全局的停止标识（Flag）来实现。

### 2.1 核心脚本适配 (`video_to_word.py`)
1. **全局中断变量**：在模块顶层定义 `STOP_REQUESTED = False`。
2. **中断检查点植入**：在所有长耗时的循环内部（例如遍历视频的 `for video_path in videos` 循环，以及 `step2_extract_frames` 中的 OCR 处理循环 `for i, frame_path in enumerate`），在每一次迭代的开头检查 `if STOP_REQUESTED:`。
3. **异常触发**：若检测到停止请求，通过抛出一个自定义的异常（如 `raise InterruptedError("用户手动终止了任务")`）或者直接 `return` 来安全、迅速地跳出整个执行堆栈，确保后续步骤不会再被执行。

### 2.2 界面交互与控制 (`gui_launcher.py`)
1. **停止按钮 UI**：在“🚀 开始批量处理”按钮同排增加一个红色的“🛑 停止处理”按钮。
2. **按钮状态管理**：
    * 初始及空闲状态：“开始”可用，“停止”禁用。
    * 任务运行期间：“开始”禁用，“停止”可用。
    * 点击“停止”后：立即将“停止”按钮禁用（防止连点），界面显示“正在中止...”。
3. **信号传递机制**：
    * 定义 `stop_process()` 方法。当用户点击停止按钮时，执行 `import video_to_word as v2w; v2w.STOP_REQUESTED = True`。
4. **清理与恢复**：
    * 在 `worker_thread` 的 `finally` 块中，无论任务是成功、失败还是被中断，都将 `v2w.STOP_REQUESTED` 重置为 `False`，并恢复界面按钮的初始状态。
    * 在异常捕获中特判 `InterruptedError`，打印“⚠️ 任务已被用户手动终止”并弹窗提示，而不是当作系统崩溃错误处理。

## 3. 预期效果
用户可以在视频转录或 OCR 去重的任何时刻点击“停止”按钮。虽然当前正在执行的那一行代码（如正在读取某张图片）必须跑完，但在下一行代码执行前的“检查点”上，程序会立刻捕获到停止指令并安全退出，从而彻底告别“只能点右上角红叉”的尴尬。
